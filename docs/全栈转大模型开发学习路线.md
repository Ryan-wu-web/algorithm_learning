# 全栈开发转大模型开发学习路线

> 适用对象：已有前后端、数据库、接口开发和部署经验，希望转向大模型应用开发、RAG、Agent、模型微调与推理部署的开发者。
>
> 建议周期：16 周，每周 12～18 小时。若只能业余学习，可将每一周延长为两周。

## 1. 路线定位

抖音图片里的路线覆盖得很广，包括 Python、Transformer、预训练、微调、压缩、RAG、Agent、多模态、评测和部署。这些方向本身没有问题，但如果按“先学完全部理论，再做项目”的方式推进，学习周期会很长，也不容易形成求职作品。

对全栈开发者，更合适的主线是：

```text
Python 工程化
→ 大模型 API 与上下文工程
→ RAG
→ Agent 与工作流
→ 评测、安全与可观测性
→ PyTorch 与 Transformer 原理
→ LoRA / QLoRA 微调
→ 推理部署与性能优化
```

职业方向建议按以下顺序考虑：

1. **大模型应用开发 / AI 应用工程师**：最适合利用现有全栈能力，优先投入。
2. **RAG / Agent 工程师**：企业需求较多，需要后端、数据和系统集成能力。
3. **模型微调与推理工程师**：作为第二阶段能力，补齐 PyTorch、训练和部署。
4. **基础模型预训练与算法研究**：需要较强数学、算法和算力基础，不作为当前首要目标。

## 2. 最终学习目标

完成这条路线后，应能够独立完成以下工作：

- 使用 Python 构建结构清晰、可测试的 AI 后端服务。
- 接入主流大模型 API，并处理流式输出、结构化输出、工具调用和多轮上下文。
- 构建带引用、可评测、可追踪的企业级 RAG 系统。
- 使用工作流或 Agent 完成多步骤任务，并控制循环、超时和成本。
- 建立离线评测集，评估检索质量、答案质量、延迟和费用。
- 理解 Transformer、Embedding、注意力机制、LoRA 和量化的核心原理。
- 使用开源模型完成 LoRA / QLoRA 微调和基础推理部署。
- 将 AI 服务通过 Docker、日志、监控、鉴权和限流投入实际使用。

## 3. 第一阶段：Python 与 AI 工程基础

**建议时间：第 1～2 周**

已有全栈经验时，不需要从语法教材第一页开始。重点是把 Python 写到可以承担生产后端和数据处理任务的程度。

### 学习内容

- Python 类型系统：`list`、`dict`、迭代器、生成器、装饰器、上下文管理器。
- 类型标注：`typing`、泛型、`Protocol`、Pydantic 数据模型。
- 异步编程：`async` / `await`、并发请求、连接池、超时和取消。
- 工程结构：配置、日志、异常、依赖注入、分层和模块边界。
- Web 服务：FastAPI、请求校验、鉴权、中间件、SSE 流式响应。
- 测试与质量：pytest、Ruff、类型检查、pre-commit。
- 数据处理：NumPy、Pandas 基础；暂时不需要深挖数据科学分析。

### 阶段项目

实现一个统一的大模型聊天网关：

- 支持至少两个模型供应商。
- 支持普通响应和流式响应。
- 使用统一的请求、响应数据结构。
- 包含超时、重试、错误映射、日志和简单用量统计。
- 使用 pytest 覆盖核心服务逻辑。

### 完成标准

- [ ] 能独立创建结构清晰的 FastAPI 项目。
- [ ] 能用异步方式并发调用外部 API。
- [ ] 能为核心逻辑编写单元测试。
- [ ] 能解释超时、重试和幂等性的区别。

## 4. 第二阶段：大模型 API 与上下文工程

**建议时间：第 3～4 周**

这一阶段先把模型“用明白”。Prompt 只是其中一部分，更重要的是输入输出契约、上下文管理、可靠性和成本。

### 学习内容

- Chat Completions / Responses 类接口的基本抽象。
- System、User、Assistant、Tool 消息的职责。
- Token、上下文窗口、采样参数和停止条件。
- Prompt 设计：任务、上下文、约束、示例和输出格式。
- Few-shot、任务拆解、反思与结果校验。
- JSON Schema / Pydantic 结构化输出。
- Function Calling / Tool Calling。
- 多轮对话的历史裁剪、摘要和状态管理。
- 缓存、重试、限流、降级、费用统计和模型路由。
- Prompt Injection、敏感信息泄露和工具权限边界。

### 阶段项目

在聊天网关上增加“结构化任务助手”：

- 从自然语言中提取任务、优先级和截止日期。
- 模型输出必须通过 Pydantic 校验。
- 失败时执行有限次数的修复或重试。
- 增加一个天气、搜索或数据库查询工具。
- 记录每次调用的模型、Token、耗时和结果状态。

### 完成标准

- [ ] 能稳定得到可解析的结构化输出。
- [ ] 能实现一次完整的工具调用闭环。
- [ ] 能控制上下文长度和调用费用。
- [ ] 能识别并缓解常见 Prompt Injection 风险。

## 5. 第三阶段：RAG 检索增强生成

**建议时间：第 5～7 周**

RAG 是转型中的核心模块。不要只做“上传 PDF 然后聊天”的演示，应学习完整的数据、检索、生成和评测链路。

### 学习内容

#### 文档处理

- PDF、Markdown、HTML、Office 文档的解析。
- 文档清洗、标题层级、表格和元数据保留。
- 固定长度、递归、语义和按文档结构切块。
- Chunk 大小、重叠长度与召回效果的关系。

#### 检索

- Embedding 的含义、相似度和向量维度。
- 向量检索、BM25 关键词检索和混合检索。
- PostgreSQL + pgvector，了解 Milvus、Qdrant 等专用向量库。
- Metadata Filter、查询改写和多路召回。
- Reranker 重排、去重和上下文压缩。

#### 生成

- 基于证据回答并提供引用。
- 证据不足时明确拒答。
- 多文档冲突处理和来源优先级。
- 流式回答、引用定位和会话记忆。

#### 评测

- Recall@K、MRR、NDCG 等检索指标。
- 答案相关性、忠实度、完整性和引用正确性。
- 人工标注集、合成问题集与回归测试。
- 延迟、Token 和单次问答成本。

### 阶段项目

构建“个人技术知识库”：

- 支持 Markdown、PDF 和网页内容导入。
- 保存文档、分块、版本和来源元数据。
- 使用混合检索与可选重排。
- 回答必须带可点击的来源引用。
- 支持文档增量更新和删除。
- 建立至少 30～50 条评测问题。
- 提供检索结果、评分、耗时和调用费用的调试页面。

### 完成标准

- [ ] 能说明切块策略为什么影响最终答案。
- [ ] 能对比纯向量、BM25 和混合检索效果。
- [ ] 能构建可重复运行的 RAG 评测集。
- [ ] 能定位问题发生在解析、召回、重排还是生成阶段。

## 6. 第四阶段：Agent 与工作流

**建议时间：第 8～9 周**

优先掌握可控工作流，再学习高自主 Agent。生产系统中，可观察、可恢复的流程通常比完全自由规划更可靠。

### 学习内容

- Tool Calling、工具描述、参数校验和权限控制。
- 状态机、节点、条件分支、循环和人工确认。
- Planning、Reflection、Memory 的用途和风险。
- 短期状态、长期记忆和业务数据库的边界。
- 工具失败重试、超时、熔断、补偿和幂等性。
- Agent 最大步数、成本预算和终止条件。
- MCP 的基本概念：工具、资源和提示的标准化接入。
- LangGraph 等工作流框架；同时保留直接调用模型 API 的能力。

### 阶段项目

为知识库增加“工程任务助手”：

```text
用户提出问题
→ 判断是否需要检索
→ 检索内部知识库
→ 必要时调用外部工具
→ 生成带引用的结论
→ 高风险操作请求人工确认
→ 保存过程和结果
```

可选工具：代码仓库搜索、工单查询、数据库只读查询、网页搜索、任务创建。

### 完成标准

- [ ] 能区分普通工具调用、工作流和自主 Agent。
- [ ] 能限制 Agent 的执行步数、费用和工具权限。
- [ ] 能让失败流程从中间状态恢复。
- [ ] 能查看每一步的输入、输出、耗时和错误。

## 7. 第五阶段：评测、安全与可观测性

**建议时间：第 10 周**

能调用模型不等于能交付大模型系统。评测和可观测性是应用从演示走向生产的分界线。

### 学习内容

- 建立黄金数据集与典型失败案例集。
- Prompt、模型、Embedding、切块和检索策略的版本化。
- 离线评测、在线反馈、A/B 测试和回归门禁。
- LLM-as-a-Judge 的适用场景、偏差和人工抽检。
- Trace、日志、指标和调用链。
- 首 Token 延迟、总延迟、成功率、Token、费用和缓存命中率。
- Prompt Injection、越权工具调用、数据泄露和输出审核。
- 多租户数据隔离、鉴权、限流、审计和密钥管理。

### 阶段项目

- 建立一套命令即可运行的 RAG 回归评测。
- 生成不同版本的质量、延迟和成本对比报告。
- 为知识库增加用户反馈与失败案例回收。
- 增加工具白名单、危险操作确认和敏感信息过滤。

### 完成标准

- [ ] 每次更换模型或 Prompt 后都能量化比较效果。
- [ ] 能追踪一次请求经过的检索、模型和工具步骤。
- [ ] 能说明系统的主要安全边界和攻击面。

## 8. 第六阶段：PyTorch 与 Transformer 基础

**建议时间：第 11～12 周**

此时已经有应用经验，再学习模型原理会更容易建立直觉。目标不是立即训练基础模型，而是为微调、部署和问题排查打基础。

### 数学基础

- 向量、矩阵、点积、矩阵乘法和范数。
- 概率分布、交叉熵、KL 散度。
- 导数、梯度、链式法则和梯度下降。

### PyTorch

- Tensor、广播、设备和数据类型。
- Autograd、计算图、反向传播。
- `nn.Module`、优化器、损失函数和 DataLoader。
- 训练循环、验证、保存和加载权重。
- 混合精度、梯度累积和显存基本估算。

### Transformer

- Tokenization、Embedding 和位置编码。
- Q、K、V 与 Self-Attention。
- Multi-Head Attention、残差连接、LayerNorm、FFN。
- Encoder、Decoder、Causal Mask。
- 预训练、指令微调、偏好对齐的区别。
- 推理阶段的自回归生成与 KV Cache。

### 阶段项目

- 用 PyTorch 完成一个小型文本分类器。
- 手写一个简化版 Self-Attention，并验证输入输出形状。
- 使用 Hugging Face 加载开源模型，完成 Tokenize、推理和结果解析。

### 完成标准

- [ ] 能解释 Attention 为什么可以建模 Token 之间的关系。
- [ ] 能读懂基础训练循环并排查常见维度错误。
- [ ] 能区分训练显存和推理显存的主要组成。

## 9. 第七阶段：LoRA / QLoRA 微调

**建议时间：第 13～14 周**

微调应解决明确问题，例如稳定输出风格、掌握特定格式或提高垂直任务表现。若问题主要是知识时效性或私有知识查询，通常优先使用 RAG。

### 学习内容

- SFT 数据格式、指令模板和 Chat Template。
- 数据清洗、去重、训练集与验证集拆分。
- LoRA 的低秩思想、Rank、Alpha 和 Target Modules。
- QLoRA、4-bit 量化和显存节省原理。
- Hugging Face Transformers、Datasets、PEFT、TRL。
- 学习率、Batch Size、Epoch、梯度累积和过拟合。
- Adapter 保存、加载、合并和版本管理。
- 微调前后使用同一评测集对比，防止只凭主观样例判断。

### 阶段项目

选择一个小参数开源指令模型，完成垂直任务微调：

- 准备高质量训练数据和独立评测集。
- 使用 LoRA 或 QLoRA 训练。
- 记录配置、损失、显存、耗时和模型版本。
- 对比基础模型、Prompt 优化和微调模型。
- 将 Adapter 接入前面的 AI 助手。

### 完成标准

- [ ] 能判断一个需求更适合 Prompt、RAG 还是微调。
- [ ] 能完成一次可复现的 LoRA / QLoRA 训练。
- [ ] 能用客观评测证明微调是否有效。

## 10. 第八阶段：部署与推理优化

**建议时间：第 15～16 周**

### 学习内容

- Docker 镜像、环境变量、健康检查和持久化。
- 模型服务与业务 API 分离。
- vLLM、TGI、Ollama 等推理工具的定位和差异。
- Continuous Batching、KV Cache、吞吐和延迟。
- FP16 / BF16、INT8 / INT4 量化的基本取舍。
- 并发控制、队列、限流、超时和熔断。
- GPU 显存、利用率、吞吐、P50 / P95 延迟监控。
- 灰度发布、回滚、模型版本和 Prompt 版本管理。

### 阶段项目

- 用 Docker Compose 部署应用、PostgreSQL、Redis 和模型服务。
- 支持云模型与本地模型切换或降级。
- 增加健康检查、日志、指标、限流和缓存。
- 进行简单压测，记录并发、吞吐、延迟和资源占用。
- 编写部署说明和故障排查清单。

### 完成标准

- [ ] 能估算模型部署所需显存。
- [ ] 能解释吞吐与延迟之间的取舍。
- [ ] 能把完整系统在新环境中重复部署。

## 13. 学习与开发环境

你的 `PyCharm + Claude CLI` 方案是可行的，尤其适合 Python 后端和大模型工程。建议补齐下面的工具链。

### 推荐组合

```text
Windows 11
├─ PyCharm Professional：主要 IDE、调试、数据库与测试
├─ WSL2 + Ubuntu：接近 Linux 服务器的开发环境
├─ Claude CLI：代码阅读、实现辅助、重构和测试协作
├─ uv：Python 版本、虚拟环境和依赖管理
├─ Git：版本管理
├─ Docker Desktop：数据库、向量库和服务编排
├─ Jupyter：模型和数据实验
├─ PostgreSQL + pgvector：业务数据与向量检索
└─ Redis：缓存、限流、会话和任务状态
```

### 为什么建议增加 WSL2

- 大多数 AI 开源工具首先支持 Linux。
- 与云服务器、Docker 和 GPU 环境更接近。
- Shell、依赖编译和部署脚本兼容性更好。
- 后续使用 CUDA、本地模型和推理框架时更省心。

如果当前主要调用云端 API，也可以先在 Windows 原生环境开始；进入本地模型、微调和部署阶段后，再将项目迁入 WSL2。

### Python 工具建议

- **依赖与环境**：优先 `uv`，一个项目一个虚拟环境，并提交锁文件。
- **代码质量**：Ruff 负责格式和静态检查，pytest 负责测试。
- **配置管理**：使用 `.env` 保存本地配置，但不要提交真实密钥。
- **数据校验**：使用 Pydantic 定义模型输入、工具参数和结构化输出。
- **Notebook 边界**：Jupyter 用于实验，稳定逻辑及时迁入正式 Python 模块。

### PyCharm 建议

- 将项目解释器配置为 WSL 中的 `uv` 虚拟环境。
- 配置 Ruff 和 pytest，保存或提交前执行检查。
- 使用 HTTP Client 调试流式接口和工具调用接口。
- 使用 Database 工具查看 PostgreSQL、pgvector 和检索结果。
- 为 API 服务、测试、评测脚本分别创建运行配置。

### Claude CLI 使用原则

Claude CLI 可以明显提高开发速度，但要让它成为工程协作者，而不是替代自己的理解：

- 先让它阅读项目约定、数据流和测试，再要求修改。
- 将任务拆成小范围、可验证的改动。
- 要求同时补测试，并自己阅读关键路径。
- 对数据库迁移、权限、并发和费用相关改动重点复核。
- 不要在提示、日志或仓库里暴露真实 API Key 和用户隐私数据。
- 项目中维护清晰的开发说明、测试命令和架构约束，降低上下文误判。

## 14. 主作品项目：AI 知识与工程助手

建议 16 周围绕一个持续演进的主项目学习，避免每周都做互不相关的小 Demo。

### 用户侧功能

- 账号、工作空间和知识库管理。
- 上传 PDF、Markdown、网页等资料。

- 保存、搜索和分享历史会话。

### 管理与调试功能

- 文档解析、切块和索引状态。

- Prompt、模型、Embedding 和知识库版本。

- 评测集管理和版本对比报告。

### 推荐架构

```text
Web 前端
   ↓

        ↓
PostgreSQL + pgvector / Redis / 对象存储
        ↓
云端模型 API 或本地推理服务
```

## 18. 最终路线总结

你的优势不是从零开始，而是已经具备完整的软件工程视角。大模型开发仍然需要接口、数据库、缓存、异步任务、权限、部署、监控和用户体验，这些全栈经验都会直接复用。

最值得坚持的原则是：

1. **先做应用闭环，再补模型深度。**
2. **围绕一个主项目持续迭代，不堆零散 Demo。**
3. **从第一天开始记录质量、延迟和成本。**
4. **每个新框架都先理解它解决的问题，再决定是否引入。**
5. **RAG 解决知识问题，微调解决行为与任务适配问题，不要混用。**
6. **PyCharm + Claude CLI 可以作为主力组合，建议搭配 WSL2、uv、Docker 和完善的测试工具链。**

完成 16 周后，目标不是“学完所有大模型知识”，而是拥有一套能展示、能评测、能部署，也能清楚说明工程取舍的大模型应用系统。这会比一长串课程记录更有说服力。
